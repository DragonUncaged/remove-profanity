This battery is designed and owned by this project. Nothing in it is taken from
another library's tests, README or issue tracker, and it deliberately includes
cases remove-profanity fails. Most evasion cases are generated by applying one
transform function per taxonomy axis to every language, so no author choice
decides which transforms a language receives. See benchmark/METHODOLOGY.md.

=== WHAT EACH LIBRARY CLAIMS ===
Scored primarily on the languages it claims. A miss on unclaimed ground is
reported as coverage not attempted; a false positive counts everywhere.

functions for every language. named = hand-written, for the axes a function
cannot express (morphology, transliteration spread, script doublets, lexicon).

look like, so the numbers are printed rather than described.

=== PERFORMANCE: returning spans, not a boolean ===
obscenity is the only rival that reports match positions, so scan() vs
getAllMatches() is the one like-for-like row for a consumer who needs to know
WHERE the match is — to censor it, to highlight it, or to log it. The two are
not equivalent in what they hand back: scan() returns lemma, surface, tier,
language, severity, categories and the span; getAllMatches() returns a term id
and indices, and the caller looks the word up itself. allprofanity,
leo-profanity, bad-words and @2toad have no equivalent call and are absent from
this table rather than scored zero.

=== PERFORMANCE: cost vs dictionary size (ms per isClean) ===
One matcher per pack subset, same texts, built and timed back to back.
Under O(text × dictionary) — one pass per blacklisted term, which is how a
regex-per-word filter works — 4.8x the lemmas would cost about 4.8x the time.
It does not, and it is not flat either: read the marginal column, which is what
the next pack costs on top of the row above it.

These rows are comparable to each other — same process, back to back — and NOT
to the grid at the top of the section, which was measured earlier in the run.
Two things in the shape are worth stating plainly. Lemma count does not drive
the cost: the 56-lemma Hindi pack ALONE costs more on pure ASCII than the
70-lemma English pack alone, because what a pack contributes is surface
patterns and live tiers, not headwords. And the curve flattens hard rather than
staying level: the first pack added to English is the expensive one, and the
nine packs after en+hi add 212 lemmas for a few percent between them.
"Sub-linear, and flat once the tiers are live" is the honest description of
this curve; "flat in dictionary size" is not.
